# Old Admin Data Consolidation Design

## Goal

Make the new admin database authoritative for operations by replacing its current operational/property data with the old admin database data, while preserving new booking/payment history and public pricing configuration. Add a safe test-booking removal action that unblocks dates without contacting Razorpay.

## Approved approach

Use a direct database-to-database migration driven from a local, one-use script. The script will connect with source and destination PostgreSQL credentials supplied locally, create encrypted backups, perform a dry-run inventory, and then execute the destination changes transactionally.

The old database remains unchanged. No source records are deleted. Destination changes occur only after backup and dry-run validation.

## Alternatives considered

1. Temporary export/import API endpoints. This avoids local database credentials but creates a sensitive migration surface and requires temporary production deployments.
2. Manual recreation through the admin UI. This cannot reliably preserve historical events, blocks, overrides or identifiers.
3. Direct transactional migration. This is selected because it supports backups, complete dependency ordering, deterministic remapping and rollback.

## Preserved destination data

The migration preserves:

- `bookings` and their booking-night prices;
- payment events, payment jobs and refund-job aliases;
- booking attempts and booking events;
- notification outbox history;
- local calendar entries generated by preserved bookings;
- active inventory nights owned by preserved website bookings;
- property pricing, overrides and public-room slug/booking-enabled configuration for matching imported properties;
- audit events required by preserved bookings and payments.

## Replaced destination data

The old database is authoritative for:

- properties and property settings;
- listings and inbound iCal configuration;
- external iCal events, including historical state;
- manual direct reservations and blocked periods;
- operation overrides;
- cleaning tasks;
- sync history;
- non-booking operational audit history.

Destination operational rows not preserved above are removed inside the migration transaction before the source data is inserted.

## Identity and collision rules

Properties match by normalized property name. Listings match within a property by normalized display name, with decrypted inbound iCal URL used as a secondary identity check. Matching records are represented once; source operational fields win.

Preserved destination bookings are remapped to the matching imported property. If a booking property has no source match, a minimal archived destination property is retained solely to preserve booking history and is hidden from active property/calendar views.

Destination public pricing is remapped to the matching imported property. Public room slugs remain unique. No duplicate listing is created for a matching property/listing pair.

Actor references are mapped by authenticated-user email. Password hashes and sessions are not copied. If an old actor has no matching destination user, its write/audit reference is mapped to the destination administrator performing the migration and the original source actor ID is recorded in migration metadata.

## iCal handling

Inbound iCal URLs are decrypted with the old `ICAL_ENCRYPTION_KEY` and re-encrypted with the new key. Ciphertext is never copied blindly. Outbound token hashes are preserved so known tokens remain valid on the new host; the old host is not retired until outbound consumers are checked or redirected.

## Inventory rebuilding

After import and booking remapping, the migration rebuilds active inventory nights from:

- imported active external iCal events;
- imported active manual blocks/direct reservations;
- preserved active website bookings and holds.

Any overlapping owners are reported during dry run. The apply phase stops rather than silently choosing an owner.

## Test-booking removal

The admin Bookings page gains `Remove test booking & unblock dates` for bookings whose stored `razorpay_key_id` starts with `rzp_test_`.

After the administrator types the booking reference, the action transactionally:

- changes the booking to cancelled;
- sets `cancellation_reason` to `admin_test_cleanup`;
- archives the booking with the current administrator as actor;
- releases website hold and booking inventory nights;
- archives its generated local calendar entry;
- reconciles the affected property/date range;
- writes booking and audit events;
- does not create a refund job and never calls Razorpay.

The booking remains available under the Archived view for payment/audit history.

Live-key bookings never receive this action and must continue through the refund workflow.

## Safety and verification

Before apply:

- source and destination database fingerprints must differ;
- both schemas and required columns are validated;
- a source and destination snapshot is written to a permission-restricted temporary directory;
- table counts, match decisions, booking remaps and overlaps are printed in a dry-run report;
- the destination backup is restorable.

After apply:

- imported table counts equal the dry-run plan;
- no duplicate normalized property/listing identities exist;
- every imported listing decrypts with the destination iCal key;
- every preserved booking resolves to a property and retains its payment/history rows;
- pricing slugs remain unique and resolve to active imported properties;
- active inventory has at most one owner per property/night;
- the calendar, properties, pricing and bookings service tests pass against the migrated database;
- source counts are unchanged.

## Credentials and cleanup

The one-use script requires source/destination `DATABASE_URL` and `ICAL_ENCRYPTION_KEY` values in an ignored local environment file. Secrets must not be pasted into source code, committed, printed or included in migration reports. Temporary snapshots and credentials are removed only after verification and explicit retention requirements are satisfied.

## Deployment order

1. Implement and deploy the test-booking removal action.
2. Confirm the new production schema and application are healthy.
3. Run migration dry-run and review conflicts.
4. Apply the migration transaction.
5. Verify all counts, relationships, iCal decryption and inventory.
6. Keep the old database and project unchanged until the new admin is accepted as authoritative.
